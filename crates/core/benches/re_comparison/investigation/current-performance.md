# Basic generation and parallel CPU investigation

Follow-up to the [allocator comparison](allocator-comparison.md), 2026-10-13.
Native aarch64 Linux VM, ten logical CPUs, Rust 1.89.0 release, **mimalloc v2
with option 26 = 0** throughout. No other allocators were measured.

The investigation ran sequentially against temporary copies of the then-current
libraries. Production was unchanged during those experiments. The improvements
were subsequently integrated at the user's request; see the production section
below. `investigate_current.py` adds
phase timers and controlled variants; `--counts` additionally enables thread-local
operation counters. Counter-enabled timings are diagnostic, not the performance
comparison. The phase-only builds compile away per-operation counter increments.
Some small variant scaffolding remains in their baseline; measured baseline
times closely match the previous uninstrumented results.

`diagnose_current.py` measures process user and system CPU with `getrusage` and
compares complete canonical results across every variant. Canonical files are
retained alongside the raw records. Basic's reference is a newly measured old
parallel run, including both saturations; ordinary maximization uses the same
frozen snapshots as earlier reports. No RE conversion, transport or GUI timing
is included. Process CPU includes setup and teardown, while kernel elapsed
excludes them. Phase CPU uses process-wide `/proc/self/stat` ticks (100 Hz on
this VM); it is approximate and reported separately from exact resource totals.

## Basic: global history is consulted too late

The current engine has a global `seen` history, but generation only consults a
separate **per-parent-pair** history. It constructs a candidate, tests it against
both parents and the pair's retained candidates, and often solves flows for those
tests. Only after all jobs finish does `new_candidates` consult the global history.
Thus a candidate already generated by an earlier pair/batch is repeatedly processed.

The old generator checks its shared global history immediately after constructing
and normalizing the candidate. In the counted run, it discarded **16.30 million
of 16.42 million candidates** at that point, before local antichain pruning.

Measured counts for the degree-seven active saturation:

| Operation | Old parallel | Current new | New, earlier history query |
| --- | ---: | ---: | ---: |
| Parent pairs | 255,150 | 255,150 | 255,150 |
| Constructed configurations | 16,423,911 | 22,191,147 | 22,191,147 |
| Earlier global-history rejections | 16,304,718 | 0 | 20,479,716 |
| Local containment checks | 548,340 | 107,535,025 | 7,138,536 |
| Global containment checks | 5,145,254 | 9,342,932 | 9,534,171 |
| Flow calls, local plus global | 3,988,406 | 54,555,110 | 6,519,936 |

The prototype reads the existing immutable history during each generation batch;
it does **not** introduce a contended shared set or require `Hash` bounds. Entries
produced within that same batch can still repeat. This explains why its history
rejections need not equal the old continuously updated shared history.

In the phase-only baseline, generation takes **40.97 s** and history/global
pruning **2.76 s**, out of 43.74 s total. Moving the history query earlier reduces
generation to **14.24 s**, while global processing remains approximately 2.68 s.
The issue is repeated local work rather than slow final global pruning.

## Basic: redundant union choices and late exchange rejection

The old `good_unions` groups operand pairs producing the same join and discards
dominated operand choices within each group. The new generator considers all
incomparable operands. The old/prototype rule reduces union choices from
**1,975,944 to 1,450,668**, and complete matrix visits from **402,746,175 to
294,521,022**. With only this change, the first elapsed trial falls from 43.74 s
to 37.09 s: useful, but smaller than the earlier-history gain.

The current code detects dominated two-by-two exchanges in advance but applies
that rejection only to **complete** count matrices. In Basic, **380,555,028 of
402,746,175** complete matrices are immediately discarded. A further prototype
rejects the search branch as soon as both conflicting cells have positive counts.
It uses the same previously proved exchange condition, applying the rejection
earlier rather than introducing a new dominance rule. Complete result equality
is checked on the benchmark cases; production adoption still needs the normal
exhaustive/custom-algebra/cancellation verification.

Initial phase-only trials (one run each):

| Variant | Elapsed | Aggregate CPU |
| --- | ---: | ---: |
| Old parallel | 28.43 s | 280.98 s |
| Current new | 43.74 s | 417.65 s |
| Union-choice pruning alone | 37.09 s | 351.67 s |
| Earlier history query alone | 16.95 s | 148.72 s |
| Both | 15.68 s | 134.96 s |
| Both, 32 pairs per task | 13.91 s | 118.61 s |

Three-sample medians, including earlier exchange-search rejection:

| Variant | Elapsed | Aggregate CPU |
| --- | ---: | ---: |
| Current new | 44.126 s | 420.939 s |
| Earlier history, union pruning, 32-pair tasks | 13.635 s | 116.105 s |
| Above plus earlier exchange-search rejection | **8.382 s** | **66.392 s** |

The last variant is **5.26× faster** and consumes **84% less aggregate CPU**
than the diagnostic baseline. It also outperforms the old parallel result.
Counter-enabled verification confirms that it visits only **16,423,911 complete
matrices**, instead of 294,521,022 with union pruning alone: the rejected matrix
branches never reach the complete-matrix visitor. The number of constructed
configurations and downstream containment/flow calls is unchanged from the
history-plus-union prototype, isolating an enumeration improvement.

Repeated records: [current-basic-repeat.jsonl](current-basic-repeat.jsonl).

The combined prototype also finishes **fully serially in 43.806 s / 43.796 s
CPU** (one complete run). Previous uninstrumented serial references were
331.741 s new and 225.283 s old; neither was rerun for this investigation.
The prototype's ten-worker version uses about **52% more CPU** than its serial
version for about **5.23× less elapsed time**, with different production batch
sizes retained at one and ten workers. Without union-choice pruning, earlier
history plus earlier exchange rejection and grouped tasks still reaches
**9.72 s / 78.19 s CPU** on Basic (one run).

## Large fixture: one task/message per cheap parent pair

The parallel generator dispatches **741,382 separate Rayon jobs**, each of which
sends a result through a bounded synchronous channel and triggers coordinator
progress handling. The actual generation is cheap: only 945,393 complete
alignments/candidates survive across those pairs.

Grouping 32 or 128 consecutive pairs into one task preserves ordering, generated
configurations, all containment counts and complete results. It substantially
reduces task allocation and channel/synchronization traffic.

Three-sample medians, phase-only build:

| Variant | Elapsed | Aggregate CPU | System CPU |
| --- | ---: | ---: | ---: |
| Current new, ten workers | 5.186 s | 18.926 s | 5.611 s |
| 32 pairs per task | 1.935 s | 9.300 s | 0.401 s |
| 128 pairs per task | 1.882 s | 8.866 s | 0.277 s |

One directly instrumented phase comparison gives:

| Phase | Current elapsed | 32-pair elapsed | Current CPU | 32-pair CPU |
| --- | ---: | ---: | ---: | ---: |
| Generation | 3.629 s | 0.474 s | ~13.52 s | ~3.82 s |
| History/global pruning | 1.445 s | 1.368 s | ~5.17 s | ~5.18 s |

Almost all the CPU reduction occurs in generation. This establishes a scheduling
and synchronization cause independently of changing the mathematical work.
It does not separately attribute every kernel tick to channel locks, worker
wakeups or the Rayon scheduler.

## Large fixture: remaining redundant parallel pruning

The task-grouping change does not eliminate this second source of overhead.
Counted trials on current code give:

| Global containment checks | Serial pruning | Parallel pruning |
| --- | ---: | ---: |
| Recent-dominator cache | 5,201,328 | 5,377,647 |
| Existing-row scans | 36,365,958 | 46,317,686 |
| Removing old rows using new candidates | 9,745,106 | 20,070,899 |
| Comparing new candidates against peers | Included in ordered insertion | 5,248,210 |
| **Total** | **51,312,392** | **77,014,442** |

Both variants generate exactly the same 945,393 configurations and make the same
371,816 flow calls. The extra global comparisons reject before solving a flow.
Serial insertion immediately learns from admitted candidates and removes obsolete
rows. Parallel passes compare immutable snapshots; removal tests old rows against
new candidates that may themselves be dominated by another new candidate.

With generation grouped into 32-pair tasks, forcing serial pruning gives
**3.64 s elapsed / 7.65 s CPU**, versus **1.93 s / 9.15 s** with parallel pruning
in the initial trials. Thus parallel pruning has a real elapsed benefit once
generation scheduling is fixed, at a measurable extra-work cost. Reducing the
generation batch size to 512 does not help: **2.80 s / 10.03 s**, because it
increases the number of global dispatches.

A separate trial prunes new peers before using them to remove old rows. It cuts
global checks from **77,014,442 to 62,808,727**, mainly by reducing removal
checks from 20,070,899 to 5,865,184. However, the three-run medians are only
**1.925 s / 8.786 s CPU**, versus **1.930 s / 8.971 s** for its grouped baseline.
There is no convincing elapsed improvement and only a small CPU reduction.
Many removed comparisons are cheap early rejections, and the extra pass/dispatch
adds work. Comparison counts alone are therefore not proportional to CPU time.

## Avoid universal scheduling/pruning prescriptions

Five-sample matching medians confirm a slowdown from **50.28 ms / 189.63 ms CPU**
to **63.36 ms / 155.83 ms CPU** when grouping 32 pairs. Its individual jobs are
heavier and unevenly distributed. The combined prototype with earlier exchange
rejection reaches **29.15 ms / 104.01 ms CPU**, but task granularity still needs
workload-aware selection rather than a fixed chunk size for every problem.

On the large fixture, grouping plus earlier history lookup takes **1.85 s** in
the initial trial. Adding union-choice pruning raises it to **2.13 s / 11.56 s
CPU**: extra grouping work is not repaid on this sparse ordinary-set fixture.
The complete combined prototype takes **2.11 s / 11.67 s CPU**. Therefore union
pruning should be selected only where its benefit justifies its overhead.

## Recommended production work

1. Query immutable global history during generation, before local deduplication
   and containment/flow work. Preserve ordered admissions and optional derivations.
2. Apply dominated-exchange conflicts while exploring count matrices. Keep that
   generic search helper in `configurations/alignments.rs`, with ordinary visitation
   delegating to it without conflicts; the maximizer owns the dominance proof.
3. Group cheap generation jobs and amortize progress/channel traffic. Preserve
   cancellation and ordered results. Select granularity using measured workload
   cost or adaptive scheduling; fixed chunks regress matching.
4. Retain union-choice pruning where repeated joins make it profitable. It helps
   Basic but adds overhead on the ordinary large fixture.

No SAT solver replacement or allocator change is needed to obtain these gains.
Peer-first global pruning is not recommended based on the current measurements.
The tables above describe the historical prototypes. The selected changes are
now integrated; production verification and measurements are recorded below.

The early-conflict search additionally passes an exhaustive independent oracle:
**19,456 combinations** of degree-compatible two-by-two margins, allowed-cell
masks and conflict masks, compared with filtering complete matrices after the
ordinary enumerator. This oracle is now also a permanent production test.

## Production integration

The shared early-conflict search lives in `configurations/alignments.rs`.
`maximize/combination.rs` checks immutable global history before local pruning
and groups repeated union choices only for dense, untraced alignments. Sparse
alignments skip that grouping cost; traced runs retain original operand order.

`parallel.rs` uses Rayon's adaptive range splitting and work stealing. It folds
ordered item results into bounded messages, with a minimum grain scaled by item
and worker counts (at most 16 items) and a 128-item maximum. Small maps retain
single-item ranges. Completed-item progress is reported on the calling thread
once per received batch, while cancellation continues inside work and collection.
The maximizer retains bounded generation batches and ordered history updates.
Public model, algebra and API schemas are unchanged.

The before-integration kernels are frozen in `baseline/2026-10-13/`, allowing
the historical diagnostic scripts and variants to remain reproducible as
production evolves. They are benchmark fixtures, not application modules.

### Release measurements with configured mimalloc v2

Three-sample medians, measured sequentially on the same VM. Previous production
values are reused from the allocator comparison. Matching samples average 30
kernels; the other two cases run once per process. The table measures one fixed
ordinary maximum or both Basic saturations, not entire RE sequences.

| Input | Previous elapsed | Integrated elapsed | Previous CPU | Integrated CPU |
| --- | ---: | ---: | ---: | ---: |
| Matching step 10 | 48.333 ms | **26.143 ms** | 180.665 ms | **119.859 ms** |
| Large fixture step 2 | 5.010 s | **1.976 s** | 18.527 s | **9.983 s** |
| Basic fixed point | 43.823 s | **8.160 s** | 418.500 s | **66.281 s** |

The initial integrated runs also rechecked complete old/new maxima, not just row
counts, at one and ten workers. Their serial new medians are **81.649 ms**
matching, **5.800 s** large fixture and **41.734 s** Basic. The final scheduling
refinement only changes native parallel execution; those serial measurements
remain applicable. The freshly checked old parallel Basic median is 27.496 s.

The large fixture now finishes **2.54× faster** with **46% less CPU** than the
previous production version. It still consumes about **1.72× its serial CPU**,
with the extra frozen-snapshot pruning work described above. Basic finishes
**5.37× faster** with **84% less CPU**. These measurements establish gains on
these fixtures, rather than a universal workload ranking. Allocator selection
remains benchmark-only; the application allocator was not changed.

The workspace passes **126 core, 5 server and 2 wasm-adapter Rust tests**.
New permanent tests cover conflict masks, reversed indices, local history

reconstructed derivations, caller-thread progress and large-job cancellation.

`web/dist` contains the updated wasm binary.

The subsequent [Basic CPU overhead analysis](basic-parallel-cpu.md) separates
larger-generation-batch history lag, frozen parallel pruning and runtime costs.
Smaller parallel batches reduce Basic's relative CPU overhead from about 59% to
33% in controlled trials while also improving elapsed time. That policy is an
experiment, not another production change.

The [subsequent adaptive-batch comparison](adaptive-batches.md) tests five fixed
generation sizes and timing feedback. Learning from full and expensive partial
batches, targeting 10 ms of generation, reduces Basic CPU by 15% and elapsed by
7%, with the large fixture and matching effectively unchanged. This scheduling
policy is now integrated into native untraced generation; serial, wasm and
observed derivations retain fixed batches. The adaptive report records integration
verification and the old/new comparison, reusing existing measurements.

matching diagnostic samples are consequently noisier than the earlier 30-kernel
resource averages. These trials do not change the application allocator or UI.
